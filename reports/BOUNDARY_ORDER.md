# 축소 경계 주변의 선별 정렬

2026-10-28. **전체 수 재평가를 피하는 두 후보를 구현·검증했습니다. 개선은 확인되지 않아 기본 엔진은 원본 Atlas 5.3을 유지합니다.** 추가 감사에서 중요한 참조 대응이 초기 순서의 84번째에 있어, 경계 주변 후보군에 들어오지 못한다는 점을 확인했습니다.

## 구현한 방식

별도 `boundary-order-engine`에 다음 모드를 추가했습니다. 두 후보 모두 `depth=3, ply=1`에서만 동작하고, 평가 함수와 LMR 규칙은 바꾸지 않습니다. 번호는 아래 설명에서 1부터 셉니다.

- **window**: 기존 1~4위는 유지하고 5~16위의 12개만 기존 순위 점수와 한 수 뒤 평가값으로 재정렬합니다. 17위 이후는 유지합니다.
- **promote**: 기존 1~7위는 유지하고 8~24위의 17개 중 하나를 골라 8위로 옮깁니다. 나머지 수의 상대 순서는 유지합니다. 축소 조건의 `index>=8`은 0부터 세므로 8위는 축소되지 않는 마지막 자리입니다.
- **off**: 원본 순서입니다. 후보의 노드 예산 계측을 제외한 원본 결과가 점수·PV·노드 수까지 일치하는지 확인했습니다.

두 모드는 기존 정렬에 반영된 history·killer·TT 점수를 후보 비교에 유지합니다. 합법 수 집합과 원래 앞부분을 보존하고, 후보 평가 중 make/unmake 뒤 그래프와 해시가 복구되는지 검사했습니다. 취소·시간 확인은 각 후보를 만들기 전에 수행합니다.

추가 작업을 `orderingWork`로 기록합니다. 호출 수·평가 횟수·한 호출의 최대 후보 수를 분리해 저장하며 window는 12개, promote는 17개를 넘지 않도록 검증합니다. 이 수치는 노드 예산에 포함되지 않는 추가 평가 작업이므로 노드 수만으로 속도 향상을 주장하지 않습니다.

## 같은 계산량에서의 결과

기존 공개 개발 배치 5개를 사용했습니다. 안쪽 봉쇄의 잔여 벽 변형 3개, 3×3 공격·장문 각 1개입니다. 같은 기하학의 잔여 벽 변형 3개를 독립적인 실력 표본으로 보지 않습니다.

|후보|깊이 4 선택 개선/악화|5만 노드 선택 개선/악화|5만 노드 완료 깊이 감소|
|---|---:|---:|---:|
|window|0 / 0|0 / 0|0|
|promote|0 / 0|0 / 0|0|

안쪽 봉쇄의 세 조건에서 원본은 깊이 4에 각각 48,508개 노드가 필요했습니다. window는 각각 48,621개, promote는 각각 48,508개였습니다. 두 후보 모두 기존 선택의 비축소 참조 값 차이 8을 해소하지 못했습니다.

같은 배치에서 window는 98회 호출·1,176회 추가 평가, promote는 98회 호출·1,666회 추가 평가를 사용했습니다. 한 호출의 최대 후보 수는 각각 12·17로 유지됐습니다. **평가 대상을 줄이는 것은 구현했지만 선택 개선을 유지하지는 못했습니다.**

후속 시간 제한 시험의 사전 기준은 깊이 4와 5만 노드에서 개선이 있고 선택 값·완료 깊이 악화가 없는 것입니다. 두 후보 모두 개선이 없어 미달했습니다. 0.5초·4코어 새 시간 비교와 개발 대전은 진행하지 않았고 게임의 기본 엔진에도 연결하지 않았습니다.

## 왜 경계 근처만으로 부족했나

단순히 범위를 넓혀 다시 실험하기 전에 별도 `ranks` 감사 실행 파일을 추가했습니다. 원본이 고른 루트 수와 비축소 참조의 루트 수를 놓은 뒤, 각각의 상대 대응을 깊이 3 비축소 탐색으로 읽었습니다. 루트의 반복 이력과 ply를 유지한 값이 기존 분기 감사 값과 같은지도 확인했습니다.

|국면과 루트 수|참조가 고른 한 상대 대응|기존 초기 순위|window/promote 순위|기존 전체 static 정렬 순위|
|---|---|---:|---:|---:|
|안쪽 봉쇄, `h(0,0)`|`v(3,2)`|84|84|5|
|안쪽 봉쇄, `h(0,1)`|`h(0,6)`|1|1|1|
|장문, 기존 루트 수|참조 대응|76|76|10|

안쪽 봉쇄 세 가지 잔여 벽 조건에서 위 순위가 같았습니다. 새 후보군은 16위 또는 24위까지만 보므로 **84위의 수를 아예 평가하지 않습니다.** 이전 전체 static 정렬은 그 수를 앞쪽으로 올릴 수 있었지만 추가 계산이 컸습니다. 이제 필요한 작업은 단순한 순위 구간 조정이 아니라, 뒤쪽에 있는 미래 위협 대응을 저렴하게 선별하는 기준을 만드는 것입니다.

이 표는 **history·killer·TT 가산점을 제거한 초기 순위(cold rank)** 입니다. 실제 탐색 중 해당 수가 언제나 84위이거나 반드시 축소된다는 뜻은 아닙니다. 참조가 고른 수 또한 깊이 3에서의 한 최선 대응이며, 유일한 수나 게임 전체의 강제 승패를 증명하지 않습니다. 장문에서는 뒷순위 대응을 놓쳐도 현재 비교에서 루트 선택 악화는 없었으므로 모든 뒷순위 수를 반드시 보호해야 한다고 해석하지 않습니다.

## 검증과 재현

[후보 결과](boundary73/report.json), [후보 재검증](boundary73/verification.json), [상대 대응 순위 감사](boundary73/rank-audit.json), [순위 감사 재검증](boundary73/rank-verification.json)에 소스·바이너리·원본 기록 해시를 남겼습니다. 실제 실행 파일의 기존 이름 문자열과 무관하게 후보는 별도 identity로 구분합니다. 원본 소스와 바이너리는 변경하지 않았습니다.

- off/원본 깊이 3 일치: 5개 배치.
- 두 모드의 5만 노드 반복: 10쌍. 선택·점수·노드뿐 아니라 추가 평가 작업 수도 일치.
- 재검증: 후보 탐색 20개, LMR을 전부 끈 깊이 4 점수 일치 10개, 독립 분기 집합 5개.
- 순위 감사 재계산: 두 모드의 분기 총 16개. 반환한 상대 대응의 합법성과 분기 값도 확인.
- Node 테스트 92개, Rust 14개를 window·promote 각각 실행, 웹 빌드 통과.

```powershell
npm run search:boundary-build
# 새로운 결과 폴더 사용
npm run search:boundary-check -- reports/my-boundary-run
npm run search:boundary-verify -- reports/my-boundary-run
npm run search:boundary-ranks -- reports/my-boundary-run

```

기존 기록 검증에는 `reports/boundary73`을 사용하세요. 원본 native·기존 root-guard 비축소 감사 빌드가 필요하며 필요하면 `node scripts/build-native.mjs`, `node scripts/build-root-guard.mjs`로 준비합니다. 다른 바이너리 해시로 재빌드한 경우 새 결과 폴더를 사용합니다. 저장된 측정 결과를 덮어쓰지 않습니다.

## 남은 추천 우선순위

1. **뒷순위 대응을 포함하는 저비용 후보 선별**: 즉시 거리 이득이 작아도 미래 벽 위협을 줄이는 대응을 골라, 84위의 수처럼 경계 바깥의 중요한 수를 제한된 평가 후보에 포함합니다. 고정 좌표나 기보 ID는 조건으로 쓰지 않습니다.
2. **필요한 분기만 재탐색**: 선별 정보와 얕은 탐색 값이 충돌하는 경우에만 추가 계산을 배정합니다. 전체 깊이 보호나 후보 범위 확대는 피합니다.
3. **준비 벽·공역·벽 소모전의 별도 사례 확장**: 공개 개발 배치와 다른 기하학·잔여 벽·선후공 조건에서 같은 선별 규칙이 통하는지 확인합니다.
4. **0.5초·4코어와 별도 대전 검증 후 승격**: 고정 계산량 개선을 먼저 확인한 후보만 실제 시간 비교·일반/미로 대전·미사용 검증 세트로 진행합니다.
5. **외부 실력 검증과 실제 병목 계측**: 추가 평가·BFS·캐시·코어 대기를 나누어 재고 외부 엔진과 대전합니다.
