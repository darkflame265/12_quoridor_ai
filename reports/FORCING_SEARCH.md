# 강제 대응 수의 탐색 깊이 보호

기존 Native 진단은 12개 패배 국면 중 생각 시간을 늘렸을 때 선택이 달라지는 국면 4개와 탐색 시간에 민감한 차이 3개를 기록했습니다. 이것만으로 특정 벽이 패배 원인이라고 단정할 수는 없습니다. 이번 후보는 점수나 수의 정렬 순서를 바꾸지 않고 중요한 수의 깊이 축소를 막는 가설을 검증합니다.

## 새 실험 모드

`--search forcing`은 기존 legacy 정렬과 평가 계수를 유지하면서 다음 수를 LMR(뒤쪽 수의 탐색 깊이 축소)에서 제외합니다.

- 즉시 승리하는 수.
- 상대의 실제 합법 말 이동에 도착 승리가 있을 때, 그 승리를 막는 모든 합법 대응. 점프·우회 이동을 포함한 이동 규칙으로 확인합니다.
- 상대 거리 증가에서 내 거리 증가를 뺀 순수 이득이 2칸 이상인 벽. 기존 벽과의 연결 여부나 상위 4개 제한을 적용하지 않습니다.

수 후보를 삭제하지 않고, 깊이를 추가 연장하지 않으며, 원래 깊이에서 확인하도록 합니다. 후보가 많아지면 전체 탐색량이 감소할 수 있으므로 실전 검증 전에는 기본 엔진에 반영하지 않습니다. 모든 캐시는 검색 인스턴스 안에서 사용합니다.

## 재현

```powershell
npm run maze:build
node scripts/review-forcing.mjs reports/forcing62/new-review.json
npm run maze:evaluate -- --out reports/forcing62/new-development --mode cache4 --search forcing --geometry legacy --order-weight 180 --threat-weight 30 --cohort search62-v1 --split development --pairs 1 --ms 500 --cores 4 --max-plies 180
```

새 `search62-v1` 배치는 개발 625817, validation 843271, holdout 196537 시드를 사용합니다. 과거 Native v3·search55~59 및 이번 분리 사이의 중복 국면을 제외합니다. 각 출력은 새 경로를 사용합니다.

## 남은 추천 우선순위

1. 이번 미로 패배 기보에서 깊이 보호 범위와 위협 평가 후보 누락을 분리해서 분석. 거리 이득이 큰 벽을 전부 보호하는 방식을 더 좁힐 근거 확보.
2. 개선 후보를 시간 제한·새 validation·holdout으로 검증하고 통과한 후보만 기본 엔진에 반영.
3. 외부 엔진·숙련자 대전으로 실제 강도 검증.
4. 검증된 엔진을 활용한 지도 자료 생성과 GPU 학습 재검토.

## 실제 결과와 적용 판단

기존 패배 기록 167개 상태의 수 8,332개에서 원래 정렬 결과를 그대로 유지했고 가상 수 처리 후 상태 복원을 확인했습니다. 29개 상태에서 총 105개의 깊이 보호 대상이 있었고 한 상태의 최대 대상 수는 12개였습니다. 이는 보호할 수가 존재한다는 확인이며 해당 수가 패배를 뒤집는다는 증명은 아닙니다. [검토 원본](forcing62/review.json)을 참고하세요.

수당 500ms·4코어·최대 180수로 기존 Atlas 5.3과 대전했습니다.

| 배치 | 일반 | 미로 | 합계 |
| --- | --- | --- | --- |
| 개발 | 1승 1패 | 1승 1패 | 2승 2패 |
| 별도 validation | 4승 1패 1무 | 2승 4패 | 6승 5패 1무 |

전체 승수는 앞섰지만 미로 배치에서 패수가 더 많아 기존의 배치별 비퇴보 기준을 통과하지 못했습니다. **실제 기본 엔진은 Atlas 5.3을 유지**하며 holdout은 사용하지 않았습니다. 일반 배치의 소표본 우위를 전체 강도 향상으로 해석하지 않습니다. [개발 기록](forcing62/development/report.json), [검증 기록](forcing62/validation/report.json), [채택 판단](forcing62/decision.json)을 보존했습니다.

validation 전술 검사 16개를 통과했고 후보의 시간 초과는 0회였습니다. Rust 25개·Node 70개 테스트, 웹 빌드 및 기보 재검증으로 구현을 확인했습니다. 과거 실험 보고서는 당시 커밋에서 해시를 검증해야 합니다.
