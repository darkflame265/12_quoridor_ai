# 내부 대응 순서 개선 후보

2026-10-28. **내부 수 순서만 바꾸는 후보를 구현했습니다.** 기존 평가식을 이용한 정렬은 안쪽 봉쇄 3개에서 깊이 4의 선택 차이를 없앴고, 이전 내부 보호 후보보다 필요한 노드를 약 29% 줄였습니다. 다만 같은 5만 노드에서는 여전히 깊이 4를 완료하지 못했습니다. 제한 시간에서의 개선 기준을 통과하지 못해 기본 원본 Atlas 5.3은 유지합니다. 새 엔진 승격이나 실전 승률 향상을 주장하지 않습니다.

## 구현

기존 원본의 수 순서는 거리 변화·벽 연결·history·killer·TT를 사용합니다. 준비 벽에 대한 중요한 상대 대응이 뒤로 밀리는 문제를 줄이기 위해 **루트 직후 상대 노드인 ply 1**에서 두 가지 순서를 비교했습니다.

1. **routes**: 한 수 뒤 자신의 최단 경로 출구 수와 상대 출구 수 차이로 작은 순위 보정 `(ownRoutes-enemyRoutes)*32`를 합니다. 경로 전체 개수나 서로 독립인 경로의 개수를 센다는 뜻은 아닙니다.
2. **static**: 한 수 뒤의 기존 평가값 `-evaluate(child)*8`을 순위에 더합니다. 새 평가 항목이나 학습 모델을 추가하지 않았습니다. 상대가 가장 유리하게 대응하는 수를 먼저 읽도록 하는 용도입니다.

별도로 **static을 depth 3, ply 1에서만 적용**하는 scoped 후보도 구현했습니다. LMR이 일어나지 않는 얕은 깊이에서 불필요한 정렬을 피하기 위한 비교입니다. 이 후보는 반환된 기존 목록을 그대로 쓰는 비활성 범위와 활성 범위를 Rust 테스트로 구분합니다.

루트의 순서와 LMR 규칙·축소 깊이는 그대로입니다. 기존 TT·killer·history의 우선순위 보정을 유지합니다. 정렬 대상은 합법 수 목록이며, 정렬용 make/unmake 뒤 그래프·해시·합법 수 집합이 보존되는지 검사했습니다. 정렬 결과는 위치 전용 공유 캐시에 저장하지 않아 ply와 history 정보가 섞이지 않도록 했습니다.

구현은 별도 `response-order-engine`과 `response-depth-engine`에 있습니다. 원본 게임 엔진 소스와 실행 파일은 바꾸지 않았고, 실패한 후보를 게임의 안정 엔진으로 자동 연결하지 않았습니다. 출력의 엔진 문자열은 재사용한 원본 문자열이며, 실제 후보 구분은 보고서의 별도 소스·바이너리 identity와 모드로 합니다.

## 개발 기준과 결과

앞선 진단의 5개 공개 배치, 즉 안쪽 봉쇄의 잔여 벽 조건 3개와 3×3 공격·장문 각 1개를 사용했습니다. 같은 기하학의 잔여 벽 변형을 독립적인 실력 표본으로 취급하지 않습니다.

측정 전에 정한 후속 시간 제한 비교의 조건은 다음과 같습니다. **깊이 4에서 선택 개선이 있고 악화가 없으며, 5만 노드에서도 선택 개선이 하나 이상 있고 선택 값·완료 깊이 악화가 없어야 합니다.** 첫 두 후보가 미달한 후 동일한 기준으로 scoped 후보를 추가 확인했습니다. 기준을 완화하지 않았습니다.

|후보|깊이 4 선택 개선/악화|5만 노드 선택 개선/악화|5만 노드 완료 깊이 감소|후속 시간 제한 비교|
|---|---:|---:|---:|---|
|routes|0 / 0|0 / 0|0|미진행: 개선 없음|
|static|3 / 0|0 / 0|3|미진행: 깊이 감소|
|static, depth 3 한정|3 / 0|0 / 0|3|미진행: 깊이 감소|

안쪽 봉쇄의 구체적 계산량입니다.

|조건|원본 깊이 4 노드|이전 연결 벽 보호 후보|이번 static 정렬|이번 깊이 한정 정렬|
|---|---:|---:|---:|---:|
|균등 벽|48,508|72,778|51,560|51,684|
|공격자 벽 적음|48,508|72,778|51,560|51,684|
|수비자 벽 적음|48,508|72,895|51,666|51,684|

원본 선택의 비축소 참조 값 차이는 8이었고 이번 static·scoped 후보의 차이는 0입니다. 이전 보호 후보와 같은 선택 개선을 더 적은 노드로 얻었지만, 원본보다 필요한 노드는 약 6~7% 많습니다. 5만 노드에서 원본은 깊이 4, 두 static 후보는 깊이 3으로 끝나 선택 개선을 유지하지 못했습니다. scoped 후보도 단순히 적용 깊이를 줄이는 것만으로 노드 수를 줄이지는 못했습니다. 정렬 변경은 가지치기·history·재탐색 경로도 바꾸기 때문입니다.

**노드 감소는 실제 시간 단축과 다릅니다.** static 정렬은 탐색 진입으로 세지 않는 평가 계산을 추가합니다. 이 실행의 1코어 고정 깊이 시간은 통제된 속도 시험으로 사용하지 않았습니다. 후보가 개발 기준을 통과하지 못해 새 0.5초·4코어 시간 비교와 대전은 실행하지 않았습니다.

## 검증과 해석 범위

- 각 후보 실행 파일의 `off`가 원본의 깊이 3 점수·PV·노드와 일치하는지 5개씩 확인했습니다.
- 후보별 5만 노드 실행을 두 번씩 하여 선택·점수·노드가 일치함을 확인했습니다. 고정 노드는 1코어만 허용하며 BFS·순위 계산까지 같은 CPU 작업량을 뜻하지 않습니다.
- 모든 PV를 JS 규칙으로 검증했습니다. 선택한 수는 루트의 반복 이력과 ply를 유지한 별도 비축소 깊이 4 분기로 대조했습니다. 전체 참조의 최선 수를 비교 집합에 포함했습니다.
- 재검증기는 원본 보고서와 소스·바이너리 해시를 확인하고 후보 탐색을 다시 실행합니다. LMR을 모두 끈 경우에도 정렬만 바뀐 엔진의 깊이 4 점수가 원본 비축소 참조와 같은지 15회 확인합니다. 동일 점수의 수는 오답으로 처리하지 않습니다.
- 참조는 기존 수작업 평가의 깊이 4 값입니다. 쿼리도의 완전한 최선 수나 강제 승패를 구한 것이 아닙니다.

Node 테스트 91개와 웹 빌드 통과. Rust는 routes·static 각각 14개, 깊이 한정 static 15개 테스트를 통과했습니다. 보고서 재검증은 후보 탐색 총 30개, 비축소 점수 15개, 분기 집합 10개를 다시 계산합니다.

[두 정렬 후보 결과](order72/report.json), [재검증](order72/verification.json), [깊이 한정 후보 결과](order72/scoped/report.json), [깊이 한정 재검증](order72/scoped/verification.json)를 참고하세요. 이전 보호 후보의 계산량은 [이전 기록](budget71/chain-candidate.json)에 있습니다.

## 남은 추천 우선순위

1. **축소 경계의 후보만 선별 정렬**: 모든 대응을 재평가하지 않고 기존 상위권과 축소 경계 주변의 필요한 수만 비교합니다. 선택 개선을 유지하면서 원본 수준의 노드 수와 시간으로 줄이는 것이 목표입니다.
2. **필요한 분기만 재탐색**: 정렬 정보와 얕은 결과가 충돌하는 분기에만 추가 계산을 배정합니다. 일괄 깊이 보호는 피합니다.
3. **준비 벽·공역·벽 소모전 대응 확장**: 현재 다섯 공개 사례에 맞춘 개선과 일반적인 개선을 구분할 반례·별도 국면을 늘립니다.
4. **시간 제한·일반/미로 대전 검증 후 승격**: 같은 계산량 기준을 넘은 후보를 먼저 0.5초·4코어로 비교하고, 별도 대전·미사용 검증 세트를 통과한 경우만 기본 엔진에 반영합니다.
5. **외부 실력 검증과 실제 병목 측정**: 평가 계산·벽 순위·캐시·코어 간 대기 시간을 나누어 재고 외부 엔진과 대전합니다.
