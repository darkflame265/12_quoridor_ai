# 고정 계산량 진단과 연결 벽 내부 보호 후보

2026-10-28. **선택 차이의 원인을 내부 LMR로 좁혔고, 그 부분만 보호하는 후보를 구현했습니다. 후보는 계산량 대비 개선 기준을 통과하지 못해 실제 게임에는 적용하지 않았습니다.** 기본 엔진은 원본 Atlas 5.3입니다.

## 이번에 적용한 코드

- `search-probe-engine`: 원본 탐색에서 루트/내부 LMR을 따로 끄고 읽은 루트 분기를 기록하는 독립 진단 실행 파일입니다. 게임 엔진 소스와 바이너리는 수정하지 않습니다.
- 1코어 고정 노드 예산: 시간 대신 negamax 진입 횟수로 정확히 중단합니다. 다중 코어 예산은 프로세스에서 거부합니다. 벽 순위 계산·BFS·캐시 비용까지 같은 CPU 작업량이라는 뜻은 아닙니다.
- `chain-guard-engine`: 길게 이어진 벽이 있는 노드에서만 `depth=3, ply=1`의 내부 LMR을 막는 별도 후보입니다. 루트 LMR과 기존 평가 함수는 유지합니다. 가로/세로로 연속된 벽 3개를 검사하며 색상·기보 ID·고정 좌표를 조건으로 쓰지 않습니다.
- 재측정·보고서 검증 명령과 Node/Rust 회귀 검사를 추가했습니다. 진단과 후보는 게임의 엔진 선택 메뉴에 등록하지 않았습니다.

## 동일 계산량에서 무엇이 달랐나

이전 첫 측정에서 확인한 안쪽 봉쇄의 회전 배치 3개와, 3×3 공격·장문 각 1개를 사용했습니다. 5개 모두 이미 공개된 개발 사례입니다. 3개 안쪽 봉쇄는 같은 기하학에 잔여 벽만 다르므로 독립적인 실력 표본 3개로 간주하지 않습니다.

먼저 진단의 `off` 모드가 원본 5.3의 1코어 깊이 3 결과와 **점수·PV·노드 수 모두 일치하는지 5회** 확인했습니다. 이후 각 4가지 모드에서 2만 노드 실행을 두 번씩 했고 **20쌍 모두 결과·진행 기록·루트 분기 기록이 정확히 일치**했습니다. 진단 결과가 무조건 결정적이라고 가정한 것이 아니라 이 사례들에서 실제로 확인한 것입니다.

|깊이 4 조건|안쪽 봉쇄 3개에서 비축소 참조보다 낮은 수를 고른 개수|균등 벽 사례 노드 수|
|---|---:|---:|
|원본 축소 유지|3|48,508|
|루트 축소만 해제|3|43,726|
|내부 축소만 해제|0|72,778|
|모든 축소 해제|0|67,891|

따라서 이 사례는 루트만 보호해서 해결되지 않았습니다. 내부 축소를 해제하면 선택이 달라지지만, 읽어야 하는 노드도 늘었습니다. 보고 점수가 같아도 선택한 수의 실제 비축소 분기 값은 다를 수 있으므로 **엔진이 표시한 점수와 고른 수의 참조 값을 따로 비교**했습니다.

여기서 참조는 기존 수작업 평가 함수를 사용하는 깊이 4 탐색입니다. 강제 승패나 쿼리도의 완전한 최선 수를 증명한 것이 아닙니다. 참조의 전체 탐색 점수와 각 선택 수를 따로 읽은 분기 점수가 일치하는지도 검사했습니다. 루트의 반복 이력·ply를 유지합니다. 분기 추적의 fail-low 점수는 상한으로 표시했으며 정확한 값으로 사용하지 않았습니다.

## 시간 제한 실행의 변동

실제 원본 바이너리를 0.5초·4코어로 5개 배치에서 세 번씩 실행했습니다. 진단 로그의 오버헤드가 있는 실행 파일로 시간 성능을 재지 않았습니다.

- 5개 중 **4개에서 첫 수**, **3개에서 완료 깊이**가 달랐습니다.
- 1코어 고정 계산량의 결과는 반복해서 일치했습니다.
- 4코어의 공유 알파·캐시 갱신 순서와 시간 제한이 변동 요인이 될 수 있습니다. OS 부하·클럭 변동을 별도 계측하지 않았으므로 병렬 처리만이 원인이라고 단정하지 않습니다.
- 같은 깊이의 결정적인 선택 차이도 따로 남아 있어, 시간을 늘리는 것만으로 내부 축소 문제를 해결했다고 볼 수 없습니다.

## 좁은 보호 후보의 결과

연결 벽 후보는 깊이 4에서 안쪽 봉쇄 3개의 선택 차이를 없앴습니다. 하지만 2만 노드에서는 다섯 배치 모두 여전히 깊이 3으로 끝났고 선택 값의 개선이 없었습니다. 측정 전에 정한 기준은 **같은 예산에서 한 사례 이상 개선하고, 선택 값과 완료 깊이의 악화가 없어야 후속 대전으로 진행**하는 것이었습니다. 후보는 이 기준을 통과하지 못했습니다.

추가로 기존 탐색이 깊이 4를 완료하는 **5만 노드 경계**를 검사했습니다. 같은 예산에서 깊이가 떨어지는지 확인하기 위한 후속 진단이며 최초 개발 기준을 변경한 것은 아닙니다.

|배치|원본 완료 깊이|후보 완료 깊이|원본/후보 선택의 깊이 4 참조 값 차이|
|---|---:|---:|---:|
|안쪽 봉쇄: 균등 벽|4|3|8 / 8|
|안쪽 봉쇄: 공격자 벽 적음|4|3|8 / 8|
|안쪽 봉쇄: 수비자 벽 적음|4|3|8 / 8|
|3×3 가로 공격|4|3|0 / 112|
|장문|4|3|0 / 0|

5개 모두 완료 깊이가 감소했고, 3×3 공격 한 배치는 선택 값도 나빠졌습니다. **정확도를 위해 탐색을 더 하는 것만으로는 빠르고 강한 AI가 되지 않는다는 비용 문제**를 확인했습니다. 후보는 미승격이며 개발 대전을 실행하지 않았습니다. 이 결과로 인간 상대 실력이 향상되었다고 주장하지 않습니다.

## 재현

```powershell
npm run search:probe-build
# 새로운 폴더만 사용
npm run search:diagnose-budget -- reports/my-budget-run
npm run search:verify-budget -- reports/my-budget-run
npm run search:check-chain -- reports/my-budget-run
node scripts/verify-chain-guard.mjs reports/my-budget-run
node scripts/check-search-boundary.mjs reports/my-budget-run
node scripts/check-search-boundary.mjs reports/my-budget-run --verify
```

기존 기록의 검증은 `reports/my-budget-run`을 `reports/budget71`로 바꿔 `search:verify-budget`, `verify-chain-guard`, `check-search-boundary --verify`를 실행하세요. 기본 원본 native 빌드 및 기존 `root-guard-engine`의 비축소 분기 감사 실행 파일이 필요합니다. 실행 파일이 없으면 `node scripts/build-native.mjs`, `node scripts/build-root-guard.mjs`로 준비합니다. 타 플랫폼에서 다시 빌드한 바이너리는 해시가 달라 기존 기록 검증이 거부될 수 있으므로 새 측정 폴더를 사용하세요.

[진단 결과](budget71/report.json)와 [재검증](budget71/verification.json), [좁은 보호 후보](budget71/chain-candidate.json)와 [후보 재검증](budget71/chain-verification.json), [5만 노드 경계](budget71/boundary.json)와 [경계 재검증](budget71/boundary-verification.json)에 소스·바이너리·기록 해시를 저장했습니다. 기록이 있는 폴더에는 측정 결과를 덮어쓰지 않습니다. 후보의 `mode=off`는 공유한 진단 모듈의 환경 설정 이름이며 후보 보호 로직이 꺼졌다는 뜻이 아닙니다. 후보의 코드·실행 파일 식별은 별도 identity로 구분합니다.

검증: Node 90개, 진단 Rust 13개, 후보 Rust 14개, 웹 빌드 통과. 독립 재검증에서 진단 탐색 40개·분기 집합 5개·후보 탐색 10개·5만 노드 경계 탐색 20개를 다시 계산했습니다.

## 남은 추천 우선순위

1. **내부 수 순서 개선**: 깊이 3, ply 1에서 중요한 상대 대응이 축소 구간으로 밀리는 이유를 기록하고, 연결 벽의 복구·우회 대응을 앞쪽에 배치합니다. 보호 범위 확대보다 같은 노드 수의 선택 개선을 먼저 목표로 합니다.
2. **필요한 분기만 재탐색**: 모든 연결 벽 분기를 보호하지 않고, 얕은 탐색과 순위·위협 정보가 충돌하는 분기만 다시 읽는 후보를 비교합니다.
3. **준비 벽·공역의 상대 대응 기준 확장**: 장문·뒷문·벽 소모전 사례의 후속 대응을 고정하고, 필요한 평가 항목만 보강합니다.
4. **일반·미로의 별도 대전 검증**: 고정 사례와 동일 계산량 기준을 먼저 넘은 후보만 별도 대전·미사용 검증 세트로 검증하고 승격합니다.
5. **외부 실력 검증과 실제 시간 병목 측정**: BFS·수 순위·잠금 대기·코어 효율을 나누어 재고 외부 엔진과 대전합니다.
